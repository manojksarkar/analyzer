> Updated: 2026-10-31 (**Deleting a project leaves nothing behind (NW-4); migration 0019.** Branch
> `feat/next-work`. `tests/api/test_delete_project_cleans_up.py` now fills one row in EVERY table that hangs

> checks no row names it. On SQLite all 42 emptied already; on PostgreSQL the delete STOPPED:
> `document_diffs.document_id` had no delete rule, and PostgreSQL checks such a key after each cascaded
> delete (SQLite after the whole statement), so a project whose documents were compared could never be
> deleted there. Migration **0019_delete_rules** gives the five keys without one a rule: diffs and
> comparisons go with their document / version (CASCADE), a version's baseline and a job's version are
> emptied (SET NULL) -- which also lets one version be deleted. `analyzer.py setup` runs its statements
> itself before it stamps the head (it never runs migrations), so a database from before 0019 is not
> stamped without them; proved on a throwaway PostgreSQL database: refused before setup, deleted after,
> stamped `0019_delete_rules`. Files: each version's `runs/<version id>/` goes with the project too, its
> `node_modules` link (a junction) removed as a link first so nothing follows it into the real one; and a
> project is not deleted while a command-line run holds a version's writer lock (PostgreSQL can tell).
