> Updated: 2026-10-03b (**A job's scope is checked when it is requested, and a failed or cancelled job gives its version tag back.** Reported by the user: on a project created from
> `engine/config/api_create_project.sample_full.example.json`, `{"scope": {"type": "component",
> "names": ["Sample Core"]}, "version_tag": "v1"}` and then the same with group "My Sample" both
> failed. Reproduced through the API on a throwaway database; not caused by the 2026-10-03 fixture.
> **1 -- the bare names are ambiguous.** The sample's architecture has Layer1 AND Layer2, each with
> a group `My Sample` holding a component `Sample Core` (the layer-qualified-identity twin), so the
> job was accepted (202) and stopped in Phase 1: `Component 'Sample-Core' is ambiguous - 2 layers
> use that name`. Fix: `POST /jobs` checks the scope before it reserves anything --
> `pipeline_runner.scope_problem`, the engine's own `resolve_group_id` / `resolve_component_id`
> over the `layers` the job's config is written from (`_convert_layers`), a layer by exact name as
> `plan_runs` takes it -- and refuses an unknown or ambiguous name, an unknown type, or a group
> sent as a component (and the reverse) with 400 `INVALID_SCOPE` + `candidates`.
> **2 -- a failed job never freed its tag (a real bug, PostgreSQL and SQLite alike).** The second
> request got 409 `VERSION_EXISTS`: `_mark_failed` deleted the job's draft version so the tag
> could be reused, but the job row still pointed at it (`analysis_jobs.version_id`, FK with no ON
> DELETE), the delete raised `IntegrityError`, and the error was swallowed -- the comment in
> `start_job` promised the opposite. The in-memory test backend has no foreign keys, so no test
> saw it. Fix: `release_draft_version` unlinks the job, then deletes the draft (every other FK to
> `versions` cascades); used on failure and, newly, on cancel (a cancelled job kept its tag too).
> Only a DRAFT: a failed re-export keeps its finished version. Same cause in `DELETE
> /versions/{vid}`: every version a job had produced was undeletable; its jobs now let go of it
> first, kept with their `version_tag`, and it is refused (409 `JOB_ACTIVE`) while one is queued or
> running.
> **Verified:** with qualified names both jobs run through the API (v1 component, v2 group), each
> with the 2 Sample Core Dynamic Behaviour rows. Tests: `tests/api/test_start_job_scope.py`,
